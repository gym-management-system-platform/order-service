# order-service

Сервис **жизненного цикла заказа**: создание, чтение по идентификатору, смена статусов и **оркестрация саги** через Kafka. Исходящие команды и факты фиксируются в **transactional outbox** в той же БД, что и заказ.

## Роль в системе

Инициатор сценария: после `POST /orders` заказ и запись outbox коммитятся вместе. Публикатор по расписанию отправляет payload в Kafka. Входящие топики: события инвентаря (резерв, ошибка резерва, освобождение) и платежа (успех, ошибка). По ним обновляется состояние заказа, при необходимости ставятся новые outbox-события (оплата, компенсация) или вызывается компенсация с записью причины в заказ.

## Статусы заказа (`orders.status`)

В модели предусмотрены этапы жизненного цикла, в том числе: `PENDING`, `RESERVING_INVENTORY`, `PROCESSING_PAYMENT`, `SCHEDULING`, `COMPLETED`, `CANCELLED`, `FAILED`. Конкретные переходы завязаны на обработчики Kafka и бизнес-правила сервиса.

## API

- `POST /orders` — создание заказа. Тело: `userId` (UUID), `amount`, `productId`, опционально `quantity` (по умолчанию 1). Валидация через Jakarta Validation.
- `GET /orders/{id}` — заказ по UUID первичного ключа.

Контракт ошибок при подключённом `global-exception-starter`: единый JSON (поля времени, HTTP-статуса, текста и пути).

OpenAPI: Springdoc UI на базовом порту приложения (настройки в `application.yaml`).

## Таблицы (Liquibase)

### `orders`

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | UUID | Первичный ключ заказа. |
| `order_number` | VARCHAR(50), UNIQUE | Человекочитаемый номер (генерируется сервисом). |
| `user_id` | UUID | Покупатель. |
| `product_id` | UUID | Товар. |
| `quantity` | INT, default 1 | Количество. |
| `amount` | DECIMAL(19,2) | Сумма заказа. |
| `currency` | VARCHAR(3), default RUB | Валюта. |
| `status` | VARCHAR(50) | Текущий статус саги/заказа. |
| `failure_reason` | TEXT | Текст причины при отмене или ошибке (если заполняется). |
| `saga_id` | VARCHAR(100) | Идентификатор саги для корреляции событий между сервисами. |
| `created_at`, `updated_at` | TIMESTAMPTZ | Аудит времени. |

### `outbox_event`

Исходящие сообщения до отправки в Kafka.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | UUID | Ключ записи outbox. |
| `aggregate_type` | VARCHAR(50) | Тип агрегата (например, заказ). |
| `aggregate_id` | VARCHAR(100) | Идентификатор агрегата в строковом виде. |
| `event_type` | VARCHAR(100) | Тип события (создание заказа, компенсация, команда на оплату и т.д.). |
| `payload` | JSONB | Тело сообщения для брокера. |
| `status` | VARCHAR(20), default NEW | Жизненный цикл доставки: `NEW`, затем после успешной отправки обычно `SENT`, при ошибках — `FAILED` и повторы. |
| `saga_id` | VARCHAR(100) | Корреляция с заказом. |
| `retry_count`, `last_error` | INT, VARCHAR | Учёт неудачных попыток публикации. |
| `created_at`, `processed_at` | TIMESTAMPTZ | Постановка и отметка обработки. |

## Типичные сценарии

- **Новый заказ:** транзакция сохраняет `orders` + `outbox_event` с событием создания; публикатор шлёт в топик инвентаря/оркестрации согласно конфигурации.
- **Успешный резерв:** по событию инвентаря заказ обновляется, в outbox может быть записана команда на оплату.
- **Ошибка оплаты:** компенсация — событие для освобождения резерва, статус заказа к отмене, `failure_reason` при необходимости.
- **Успешная оплата:** перевод в `COMPLETED` (или следующий этап, если сценарий расширен).

## Технологии

Spring Boot 3, WebFlux, R2DBC PostgreSQL, Liquibase, Kafka, `kafka-starter`, `global-exception-starter`, MapStruct, Jakarta Validation.
